CINQFLOW · Fresh build · 2026-09-02

One data plane, a new control plane

The rebuild keeps exactly one thing from the existing system: the data-plane contract — the landing, Bronze and Silver layers and the read/write semantics cinqcare already depends on, which Postgres renders today and Databricks can render later. Everything above it is designed fresh: a thin FastAPI control plane, a queue, one AI reasoning runtime that proposes, and one deterministic engine that executes. Every promotion between layers passes an analyst approval gate.

kept landing / bronze / silver contract — Postgres renders it today kept Databricks as a second rendering of the same contract dropped chip architecture / plug-play connectors dropped the old control-plane code — new flow, ideated clean

01The shape of the system

Five tiers, one hard boundary. Deterministic code always runs first — profiling, parsing, statistics — and the AI runtime reasons over those persisted facts plus small samples, never bulk data, writing structured proposals. The deterministic engine is the only thing that moves rows. Both meet storage at a single data-plane port: a logical contract, not a database dialect.

02One feed, end to end

The vertical slice an analyst experiences: six stages, two approval gates. Nothing is promoted to a deeper layer without a human decision, and nothing the AI says becomes the system of record — its findings persist as structured rows the analyst reviews, edits and approves.

04The data plane is the contract

Compatibility with cinqcare is defined here and only here — and it is a logical contract: layers, identities, audit columns and batch semantics, declared engine-neutrally and verified against the existing implementation's schema definitions. Postgres is today's rendering of that declaration; Databricks (Delta tables + Volumes) renders the same declaration later. Compatibility means preserving these semantics, not reproducing PostgreSQL literally.

LayerContract (PG rendering today)Write ruleRead rule
landing File storage, not tables — a zone laid out {domain}/{source_system}/{feed}/{folder}/{business_date}/{filename} with folders incoming · processed · rejected · archive · parked (local FS now, object storage / Volumes later), plus a registry row per arrival in control.input_registry, which lives with workflow state — not in the warehouse. Place once, then only move between folders. UNIQUE(fingerprint) on the registry (sha256-…) is the exactly-once / replay-refusal mechanism. Replay + audit. Any batch can be reprocessed from its landed original.
bronze One table per feed — e.g. bronze.members_raw: bronze_id · feed_id · row_number · raw_row JSONB + the audit columns; indexed on batch_id. Append-only, enforced in the database (mutation-reject trigger + REVOKE UPDATE, DELETE, TRUNCATE). Source rows land 1:1, semantically untouched. AI reads samples + column metadata; the engine reads full batches for Silver runs. Bronze is never rewritten on reprocess.
silver_raw Canonical table per domain — e.g. silver_raw.members with UNIQUE(batch_id, feed_id, source_member_id) + the audit columns. Written only by an approved mapping version. Re-runs rebuild their own batch: Silver + quarantine rows for that batch_id are cleared and re-derived from Bronze. Downstream cinqcare consumers — identity resolution, Silver ODS, reconciliation.

Audit columns on every data row

source_system · ingestion_ts · batch_id · record_hash · created_ts · updated_ts. record_hash is content-derived, so a re-derived row after reprocess hashes the same.

One join key: batch_id

A short hex id threads arrival, execution, failure and reconciliation across control.batch_control, batch_stage_status, error_log, quarantine.quarantined_rows and recon.recon_history.

The balance equation

Per stage, records_in = records_out + quarantined + attributed_drops — recorded in batch_stage_status. A batch that doesn't balance is FAILED, not "mostly fine".

Split DSNs, no foreign keys

Control/platform state and the medallion live on separate connections, and the data-plane tables carry no FK constraints — identities are UUIDs and hashes minted in code. Both properties are what make the plane portable to a warehouse.

05Deliberately different this time

Decisions made against the first build's experience, stated so nobody re-litigates them mid-implementation.

No chip architecture, no plug-play connectors

The first build's port-pin registry, socket-ladder profiles, conformance modes and per-feed connector routes are not carried forward — under all of it, only two doors ever actually existed: an HTTP upload and a folder drop. The rebuild keeps exactly those as plain, explicit endpoints; SFTP or API pulls are added later as ordinary code, not plugins.

AI proposes, code disposes

Deterministic code always runs first: profiling and statistics are computed, persisted facts. LangGraph reasons over those profiles plus small samples and writes structured proposals. It never moves bulk data, never writes to the data plane, and its output is never the system of record without analyst approval.

The API never ingests inline

FastAPI handlers validate, persist state and enqueue. All profiling, landing, preview and promotion runs in workers, so a 2 GB roster never blocks a request thread.

Approved means immutable

Mapping versions are append-only. An approved vN is never edited in place; changes produce v(N+1) and re-enter the preview → approval loop.

Everything replays

Originals are preserved in landing and Bronze writes are idempotent by batch, so any layer can be rebuilt from the layer above it — the recovery story is re-run, not restore.

The old code is not the spec

Only the data plane's read/write contract is inherited. The control plane, flow and UI are ideated fresh from the requirement set, not ported.
