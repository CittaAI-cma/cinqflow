## 2. First-pass failures that were not defects

- **S2 checks (4) and the failed-run check (1).** `waitForURL` resolved on navigation; the body was read while `loading.tsx` was still streaming. The next actions on the same pages succeeded (the Forensic radio was clicked, the G1 flow ran), and `verify.mjs` re-ran the five checks with a wait for the rendered content: all pass. No product change.
- **"High-importance roles are a bounded short list."** The driver asserted ≤ 20; the model marked **27 of 45** columns `high`. This is the plan's own rule working as written: a column the glossary maps toward a canonical field is `high`, and the glossary covers most of a Fidelis roster. The UI cap held — the panel shows 12 and says "15 more high-importance columns — open Forensic". Recorded as a design observation (§4), not a defect.

## 3. Defect found and fixed

**PHI sample values on the wire.** `GET /api/uploads/{id}` masked the profile's sample *rows* but returned each PHI column's `sample_values` verbatim (17 columns on this file: member ids, names, DOB, address, …). The v2 `top_values`/`min`/`max` were already empty for PHI, and the Forensic table hid the values client-side, so nothing showed on screen — but the API response carried them. The handler now passes the whole profile through `mask_facts` (which was already used by the batch endpoints), and `tests/e2e/test_gaps.py::test_upload_detail_never_carries_phi_sample_values` pins it. Verified on the live stack after rebuilding the api container: 0 of 17 PHI columns carry sample values; non-PHI columns keep theirs.

This predates the PR series (the v1 handler had the same shape); it is the kind of gap MVP Epic 2 ("PHI masking in previews, quarantine, errors, and logs") is about.

## 4. Observations worth a decision (not defects)

- **Uploader is a constant.** The upload form defaults `uploader` to `analyst@cinqcare.com`, so the upload record does not name the BA who uploaded it (the approval does). Fixed alongside this report: the form now defaults to the signed-in user's email. The API field itself stays open until W1 gates every router.
- **Importance is coarse when the glossary is rich.** 27 "high" on 45 columns reads as "most of the file matters". A second tier (key columns and the domain's `what_it_answers` fields ahead of every glossary match) would make the recommended list sharper. Plan §7.4's question-aware weighting is the natural place.
- **Source knowledge is keyed by feed name.** A new group name means `sources/*.yaml` does not apply (domain claims become inferences, `likely_dataset` = "unregistered feed"). Expected today; the E3 feed registry is what gives a feed an identity independent of its display name.
- **G2 exports into the repository's knowledge tree on local compose.** The approval wrote
  `knowledge/mappings/approved/e2e_ba_mtnzgae9.yaml` (the "decision becomes knowledge" export)
  into the bind-mounted `knowledge/` folder, where it would have become a precedent for every
  future proposal in the domain. Removed after the run. The test suite avoids this by copying the
  tree per test; local compose does not - a test feed approved locally leaks into governed knowledge
  unless cleaned up.
- **The proposal left 23 of 45 columns `unknown`** for a well-known roster — the canonical enrollment model has no home for many roster fields (guardian, health-home flags, recertification). Expected; those are the columns the studio surfaces for a decision.

## 4a. Incident during the owner's manual pass (same day)

On the owner's own upload of the full roster (28,333 rows) the interpretation step failed with
`APIConnectionError: Connection error.` The worker log shows the OpenAI SDK's two built-in retries
(0.38s and 0.77s apart) and the failure 26 seconds after the call began; the container's DNS and TLS
to `api.openai.com` were fine when checked minutes later, the provider's status page read "All
Systems Operational", and re-running the step from the API ten minutes later succeeded in 56
seconds with the same model. Root cause: a transient transport failure during the model call that
outlasted the SDK's sub-second retries. The platform behaved as designed - the failure was recorded
on the ledger with its error, the upload went to `interpret_failed`, the screen said the original
was preserved, and a platform user could retry - but a network blip should not need a person.

Resolution (committed with this note): `intelligence/llm.py: retry_transient` wraps every provider
call with our own retries on transport-level failures (connection dropped, timeout, 429, 5xx), spaced
2s / 6s / 15s / 30s (`CINQFLOW_LLM_TRANSIENT_RETRIES`, default 4; 0 disables), on top of the SDK's.
Refusals, length stops and bad requests are not retried. The final error names the provider, the
attempts and the time spent. Covered by `tests/unit/test_llm_transient_retry.py`. Separately, an ADT
upload from 2026-09-02 (`schema_wiring_smoketest2.csv`) failed to land because its file is no longer
in `.cinqflow/landing`; that landing folder predates this branch's runs and the upload can be
re-created - unrelated to the connection error.
